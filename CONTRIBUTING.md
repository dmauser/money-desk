# Contributing to money-desk

Thanks for the interest. This repo is small and prefers focused PRs.

## Ground rules

- **Zero runtime dependencies.** money-desk uses only Node built-ins
  (`node:fs/promises`, `node:child_process`, etc.) plus `@github/copilot-sdk`
  at runtime (which the host Copilot CLI provides). PRs that add deps to
  `dependencies` are unlikely to merge.
- **ESM, Node 18+.** No CommonJS, no transpilation.
- **No test framework** — Node's built-in `node:test` runner only.
- **Architecture rules** are documented in
  [`.github/copilot-instructions.md`](./.github/copilot-instructions.md).
  Read it before changes that touch the registry or extension entry.

## Local development

```bash
npm test                          # all tests
node bin/cli.mjs --version        # smoke test the CLI
node bin/cli.mjs status           # ditto
node bin/cli.mjs init --project   # local install into a tmp dir to verify
```

## Adding a specialist

1. Append a fully-populated entry to `SPECIALISTS` in
   `extensions/money-desk/registry.mjs`.
2. Create the role markdown at `specialists/<name>/agents/<name>.md`.
3. Create one `specialists/<name>/skills/<slug>/SKILL.md` per skill.
4. Add the prefix and a canonical phrase to
   `tests/routes.test.mjs`'s `CANONICAL_PHRASES`.
5. `npm test` must pass.
6. Update the README's "The team" table.

## Adding a skill to an existing specialist

1. Append a `{ id, displayName, description }` entry to that specialist's
   `skills` array. Description **must** start with `**<displayName>** —`.
2. Create `specialists/<name>/skills/<slug>/SKILL.md`.
3. `npm test` must pass.

## Markdown style for skill playbooks

A SKILL.md is genuinely useful when an agent can execute it without
follow-up questions. Each one should cover:

- **When to use** — concrete triggers, not lorem ipsum.
- **Inputs needed** — exactly what the user must provide.
- **Workflow** — numbered steps an agent can follow.
- **Required citations** — what every number must point to.
- **Deliverable shape** — the file path and section structure of the
  produced report.
- **Notes** — gotchas, anti-patterns, caveats.
- **Determinism rules** (required, just before `## Report Quality`) —
  input keys, assumptions tied to the user or an `md_facts` key, exact
  calculation method, threshold-based decision rules, and a fixed output
  template, so the same inputs always give the same report. See
  [`docs/SKILL_DETERMINISM.md`](./docs/SKILL_DETERMINISM.md);
  `tests/skill-determinism.test.mjs` enforces the structure.

If a skill's math is more than a couple of arithmetic steps, back it with a
calculator in `extensions/money-desk/calculators.mjs` (pure, integer cents,
no dates or randomness), served through `md_calc`, and name it in a
`> **Calculator:**` line at the top of the skill's Calculation method. Add
closed-form or published-figure checks to `tests/calculators.test.mjs`.

Decision thresholds and assumed defaults are judgment calls. They are
collected in [`docs/FINANCE_REVIEW.md`](./docs/FINANCE_REVIEW.md)
(regenerated by `npm test`); when you add or change one, say why in the PR
so a reviewer with finance expertise can check it.

Never hard-code year-specific limits or thresholds in a skill; reference
the `md_facts` topic and key instead (add the figure to
`extensions/money-desk/data/facts-2026.json` with its primary source if
it's missing).

Aim for ~60–160 lines. Quality beats length.

## Versioning

Follow SemVer. Specialist additions and skill additions are MINOR. Tool
renames or schema changes that break consumers are MAJOR. Bug fixes are
PATCH.

### Release flow (keep CHANGELOG and package.json in sync)

**Every user-visible change must update both `CHANGELOG.md` and
`package.json` in the same PR.** `tests/version-sync.test.mjs` enforces
this — `npm test` (and CI, and `prepublishOnly`) will fail if the latest
`## [X.Y.Z] — YYYY-MM-DD` heading in `CHANGELOG.md` doesn't equal the
`version` field in `package.json`.

For any improvement or fix:

1. Add an entry under a new `## [X.Y.Z] — YYYY-MM-DD` heading at the top
   of `CHANGELOG.md` (above the previous release; below `## [Unreleased]`
   if present). Use `### Added` / `### Changed` / `### Fixed` /
   `### Removed` subsections per Keep a Changelog.
2. Bump `version` in `package.json` to the same `X.Y.Z`.
3. `npm test` — the `version-sync` test confirms they match.
4. Commit both files together (e.g. `chore(release): 0.11.6 — <summary>`).

If you forget the bump, the failing test message tells you exactly which
of the two to update.
